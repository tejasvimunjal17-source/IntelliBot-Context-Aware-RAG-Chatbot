## Day 5 - Conversation memory, follow-ups, Clear chat, session isolation  (CODE COMPLETE - NO LIVE LLM, NO REAL CHROMADB, NO REAL EMBEDDINGS TESTED)

**Honest status in one line:** follow-up questions, per-session memory, clarification, history limits, Clear chat and secret masking are implemented, wired into the app and tested, but only with a scripted stand-in LLM, a mock ChromaDB and a stand-in embedder. Nothing here has run against a real model, so how well a real model rewrites follow-ups is unknown.

**Design decisions**
- Earlier answers are used ONLY to interpret a follow-up. They never enter the answering prompt and never count as evidence; the standalone question goes through the unchanged Day 3/4 pipeline (retrieval from the session's own documents, grounded prompt, citation/number/file-name checks, fallback).
- Ambiguity is never guessed away: no earlier context, nothing earlier to refer to, or the model replying `CLARIFY:` -> the user is asked to clarify and nothing is searched.
- The rewrite is untrusted output: single short line, at least 3 words, shares a meaningful word with the conversation, no injection phrases, no prompt marker; otherwise a rule-based fallback (previous topic + new question) is used.
- No global history: one `ChatSession` per browser session (in `st.session_state`); the engine keeps no per-user state.
- Nothing is persisted: memory only, no disk, no logs; `repr()` hides text. Secrets are masked before a question is searched, sent, shown or stored.
- Day 4 code (`answering.py`, `prompting.py`, `llm.py`, ...) was not modified.

**Built**
- `core/memory.py` - `ChatSession` (limit, clear, redaction, interpretation history with size budget), `Turn`, `SourceNote`, `redact_secrets`.
- `core/followup.py` - follow-up detection (`is_dependent`, `refers_to_previous_answer`, `may_refer_to_history`), rewrite prompt, `parse_rewrite` validation, `resolve_followup`.
- `core/conversation.py` - `ConversationEngine.ask`, `ChatReply`.

## Day 3 - ChromaDB vector store and retrieval  (CODE COMPLETE - real ChromaDB NOT verified)

**Honest status in one line:** the real ChromaDB integration is written and wired into the app, but it has only been tested against a MOCK of the chromadb API. It has never been run against the real package.

**Decisions**
- Production vector store = real ChromaDB only. An earlier idea of a built-in fallback store was dropped on purpose: no substitute store, no fake embeddings in production. If ChromaDB is missing, the app shows a clear message and disables indexing/search (the Day 2 "embeddings only" path still works).
- `tests/fake_chroma.py` is a test double used ONLY by tests; production code never imports it.
- Session privacy: the index is shared on disk, but every search is limited to the document hashes of the current session.
- Duplicate handling is per document (file hash): identical -> skipped (no embedding call); changed chunks -> old chunks replaced; no stale leftovers.
- One collection per embedding model; cosine distance; `score = 1 - distance`.

- `core/vector_store.py` - `ChromaVectorStore` (PersistentClient, get_or_create_collection with cosine, upsert, query, get, delete, count, delete_collection), `SearchResult`, `AddReport`, friendly `VectorStoreError` / `VectorStoreUnavailableError`, input validation, thread lock, batching.

- `core/config.py` - `VECTOR_STORE_DIR`, `TOP_K` (1-50), `MIN_SIMILARITY` (0-1, default 0.2, uncalibrated); `.env.example` updated; `requirements.txt` adds `chromadb>=0.5,<2` (version range not install-tested).
